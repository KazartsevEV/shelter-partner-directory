## 1. Цель и границы

SEO должно привлекать **реальных конечных пользователей** бесплатного Nomad360 lite и **профессионалов, работающих с малым бизнесом**. Полезность калькулятора для клиентов бухгалтеров, финансовых консультантов и консультационных компаний — второй коммерческий маршрут к действующей возможности разместить калькулятор на собственном сайте.

**Приоритет:** EN (международный англоязычный поиск) → RU → KK. Приоритет касается исследования, создания страниц и тестирования. Он не разрешает переписывать утверждённый русский главный оффер задачи 6.

Две поисковые воронки:

1. **Предприниматель / стартап / малый бизнес:** вопрос о цене, себестоимости, прибыли, денежном потоке или бизнес-идее → страница с практическим ответом → соответствующий действующий расчёт.
2. **Бухгалтер / бизнес-консультант / финансовый советник:** запрос о полезном инструменте для своих клиентов или привлечении релевантных посетителей → тематический материал с действующим примером → существующий B2B-раздел «Работаете в B2B? Привлеките полезный трафик бесплатно.» → кнопка размещения на сайте.

**В объём SEO-07 не входит:** создание коммерческой кастомной модели, лид-форм, CRM, автоматической передачи контактов, SEO-услуг другим компаниям, новых расчётных функций, отдельных финансовых движков, сквозной пользовательской аналитики и изменения маркетинговых текстов задачи 6. Действующий B2B-интерфейс не переделывать.

**Контракт правдивости:** финансовая проверка (в EN может использоваться *financial validation / financial feasibility*) оценивает экономику заданного предпринимателем сценария. Она **не подтверждает рыночный спрос, намерения покупателей, гарантированные продажи или вероятность успеха**. Русский термин — «проверка коммерческой ценности бизнес-идеи», без английского слова «validation» в русской публичной копии. Учитывать действительные возможности интерфейса, а не список всех популярных бизнес-калькуляторов.

## 2. Проверенная исходная база и проблема публикации

На момент аудита main:

- Основной калькулятор расположен в файле **Marketing_calc.HTML**; стартовый HTML имеет lang="ru", один общий русскоязычный title/description. Главный hero (H1/H2/третья строка) динамически добавляется скриптом nomad360_calculator_ui.js.
- Язык интерфейса выбирается по localStorage или языку браузера; простой URL-параметр выбора EN/RU/KK в этом модуле **не обнаружен**. Не писать SEO-ссылки с несуществующим параметром lang=en, пока нет реализации и теста.
- Файл **index.html** в корне репозитория сейчас открывает **SHELTER Partner Directory**, а не Nomad360. При подключении личного домена нельзя молча считать корневой путь главной страницей калькулятора.
- В проверенном корне main нет файлов **robots.txt**, **sitemap.xml**, **CNAME**. Это результаты проверки конкретных путей, а не свидетельство отсутствия внешних настроек DNS/Pages.
- В коде имеются товарные, сервисные и портфельные сценарии V1/V2, расчёты стоимости, маркетинговых расходов, цены, налогов, собственных средств/кредита, Cash Flow и формирование отчётов. Функцию можно использовать как SEO-аргумент только после проверки действующего рабочего маршрута на опубликованном сайте.
- GitHub Insights / Traffic в PR #141 показывает **уникальных посетителей репозитория за последние 14 дней**, не трафик GitHub Pages и не число пользователей калькулятора.

**Перед реализацией:** сверить эти факты с актуальным main, опубликованной страницей и прошедшей приёмку задачей 6. Если состояние изменилось — документировать diff, а не работать по предположению.

## 3. Семантическая стратегия

### 3.1. Методика отбора

Все фразы ниже — **проверяемые кандидаты поискового спроса**, сгруппированные по известным пользовательским интентам; это **не статистически подтверждённая частотность**. В ТЗ запрещено приписывать им месячные объёмы, конкуренцию, CTR или позиции без подтверждения первоисточником.

До выпуска страниц подготовить таблицу семантики в репозитории (CSV/Markdown) со столбцами:

language | market | query | intent | audience | exact product feature | proposed landing URL | SERP date / country / evidence URL | approximate demand evidence | priority | decision | reason.

Проверять запросы через реальные Google SERP для языка/географии, Google Trends, Google Keyword Planner при наличии доступа, Яндекс Wordstat для RU, Google Search Console при наличии реальных показов. Отдельно фиксировать тип выдачи: бесплатный инструмент, объясняющая статья, шаблон Excel, платная услуга или отраслевой продукт. Считать конкурентами страницы **того же интента**, не только сайты со словом calculator. Для KK подтвердить естественность фразы в Казахстане, включая русско-казахские смешанные запросы; данные RU-поиска не принимать за KK-показы.

**Приоритизация:**
- **P0:** прямая потребность в выполняемом расчёте, явное соответствие функции, высокая вероятность перехода к калькулятору.
- **P1:** смежная информационная задача, сравнение решений, инструмент для клиентов консультанта.
- **P2:** широкие образовательные запросы вроде «как открыть бизнес» и «как привлечь клиентов» без непосредственного расчёта; работать только с узким полезным подзапросом, связанным с калькулятором.
- **Reject:** функциональности нет, пользователь ищет официальный налоговый сервис, заявку на кредит, проверенный отраслевой бизнес-план, CRM, массовую лидогенерацию или обещание заработка.

## 4. Архитектура индексируемого контента

### 4.1. Языковые входы

Сделать отдельный **реальный URL каждой из трёх языковых версий**, чтобы поисковик получал соответствующий текст уже в HTTP HTML-ответе. EN разрабатывается первым, затем RU и KK. Публично включить три версии **только после их проверки**, иначе временные альтернативы не добавлять в hreflang или sitemap.

**Текущий утверждённый хостинг — GitHub Pages, без покупки домена.** Предлагаемая структура под текущим реальным base path `https://kazartsevev.github.io/shelter-partner-directory/` (пути будущих языковых страниц пока НЕ существуют):
- `https://kazartsevev.github.io/shelter-partner-directory/en/` — английский вход;
- `https://kazartsevev.github.io/shelter-partner-directory/ru/` — русский вход;
- `https://kazartsevev.github.io/shelter-partner-directory/kk/` — казахский вход;
- тематические материалы только под тем же base path, например `/shelter-partner-directory/en/pricing/`. Для каждой опубликованной страницы обязательно HTTP 200 и уникальный ответ.
- `https://kazartsevev.github.io/shelter-partner-directory/Marketing_calc.HTML` — сохраняемый рабочий калькулятор; `https://kazartsevev.github.io/shelter-partner-directory/` пока относится к SHELTER Partner Directory. **Не переименовывать и не заменять корневой index.html.**

URL не должны определять язык только по браузеру, IP или localStorage: прямой вход EN обязан открывать английский полезный контент, RU — русский, KK — казахский. Переключение языка — обычные доступные ссылки между соответствующими URL; сохранённое предпочтение может использоваться в расчётном приложении, но не должно переопределять видимый язык конкретной индексируемой SEO-страницы.

**Выбор реализации:** статически сформированные HTML-страницы с необходимым текстом в source response (или эквивалентный pre-render на этапе сборки), обычные ссылочные переходы к существующему единому калькулятору. Нельзя делать три независимые копии финансовой модели, три огромных HTML-дубликата приложения, пустые страницы с одним CTA, iframe-only лендинги или страницы, где весь смысл появляется только после JS. Допускается минимальная общая сборка/шаблон страниц, если она совместима с GitHub Pages и проверена CI.

**Путь к реальному расчёту:** каждое SEO-вхождение содержит активную ссылку на существующий калькулятор и, где подтверждено работой, на конкретный сценарий. Старый URL Marketing_calc.HTML и его query-параметры демонстрации сохранять. Для переключения языка в калькуляторе от SEO-входа сначала выполнить отдельную проверку и при необходимости минимальную реализацию маршрутизации; **не вставлять несуществующие ?lang=en-ссылки**. Не ломать сохранённые черновики, режимы, валюты или адреса статических ресурсов в подкаталогах.

### 4.2. Тематические страницы: первый выпуск

Не создавать десятки шаблонов ради покрытия ключей. Первая волна после SERP-проверки — максимум **четыре различных интента на каждый готовый язык**; если один интент уже отвечает другой странице, объединить страницы вместо выпуска дубля.

| Тип страницы | Что обязана отвечать | Пользовательское действие |
|---|---|---|
| A. Financial feasibility / экономика бизнес-идеи | Что нужно ввести; какие финансовые итоги показывает модель; пример допущений без обещания спроса | Начать расчёт товара/услуги |
| B. Product/service pricing / себестоимость и цена | Какие прямые и косвенные расходы учитывать; как цена связана с маржой, налогами и привлечением покупателя; один короткий пример | Выбрать товар или услугу |
| C. Cash flow + multi-product / деньги и ассортимент | Разница между прибылью и денежным остатком; месячный горизонт; когда нужна модель нескольких позиций | Перейти к V1/V2 |
| D. Calculator for consultants / калькулятор для клиентов | Зачем бухгалтеру/консультанту инструмент для посетителей; какие задачи он решает; как работает уже существующее размещение | Перейти в действующий B2B-раздел |

У каждой опубликованной страницы — **собственный практический ответ, один пример с ясно помеченными условными числами или таблица вопросов/параметров, внутренние ссылки и CTA к работающей функции**. Материал консультанта не обещает автоматическую передачу заявок. Пользовательский путь от SEO-страницы до начала расчёта — не более одного осмысленного перехода, без обязательной регистрации.

**Согласованный основной экран калькулятора не превращать в статью.** Его три строки оффера, описание, преимущества, схема «О проекте», B2B-кнопка и компактный подвал остаются под контролем задачи 6. SEO-тексты размещать на отдельных страницах либо в технических метаданных там, где это не изменяет согласованный интерфейс.

### 4.3. Редакционная инструкция

Тон краткий, деловой, практический, без канцелярщины, пустых «миссий», риторики «не X, а Y» и обещаний гарантированного результата. Пример из расчёта должен действительно воспроизводиться текущими полями. Не описывать будущие AI Marketer/Content Factory как работающие функции калькулятора.

Для EN, RU и KK писать отдельный естественный текст под соответствующий интент, а не механический перевод и перестановку одних ключей. Разделить коммерческие/навигационные запросы и информационные; один URL = один основной интент, близкие запросы — поддерживающие. Избегать повторов ключевых фраз и страниц-переходников, существующих только для поискового робота.

## 5. Заголовки, метаданные, структура HTML

**Предварительные направления для title; это не разрешение менять утверждённые H1/H2:**
- EN: Free Business Calculator — Pricing, Profit & Cash Flow | Nomad360
- RU: Калькулятор бизнеса онлайн — цены, прибыль и денежный поток | Nomad360
- KK: Бизнес калькуляторы — шығын, пайда және ақша ағыны | Nomad360

Реализатор проверяет слова по SERP и функциональности; итоговые title должны быть уникальны на каждом языковом и тематическом URL. Description — самостоятельная естественная фраза о полезности и вариантах расчёта, с правдивым «бесплатно / без регистрации / в браузере» и без подтверждения спроса или гарантий результата.

Обязательные элементы каждого indexable URL:
- HTTP **200**, UTF-8, корректный Content-Type; фактический язык содержательного HTML совпадает с атрибутом html lang (en, ru, kk).
- В исходном HTML есть уникальные title и meta description, полезный видимый H1 и содержательная часть; JS не создаёт второго конкурирующего H1 после загрузки.
- Одна canonical-ссылка на окончательный публичный адрес **этой же языковой/тематической версии**. Языковые переводы НЕ канонизировать все на EN.
- Взаимные hreflang для всех **опубликованных эквивалентных** EN/RU/KK-страниц, включая ссылку на себя; абсолютные https-URL. Для страницы без перевода hreflang на несуществующий вариант не ставить. x-default только при отдельной подтверждённой общей/резервной странице.
- Доступные поисковику обычные ссылки <a href> между разделами; работающие переходы с клавиатуры и мобильного.
- XML sitemap с **только реально доступными каноническими URL**; robots.txt, разрешающий целевые публичные страницы. Не добавлять в sitemap локальные черновики, служебные исходники, демо-параметры, дубли и несуществующие пути.

## 12. Матрица on-page SEO: готовые ориентиры title, H1 и description

**Правила для Codex:** это редакционные кандидаты, которые уточняются по SERP, но менять утверждённый H1/H2 в `Marketing_calc.HTML` запрещено. ## 13. Контентное ТЗ каждой страницы: не тексты ради объёма, а проверяемый ответ

Каждая новая информационная страница — **самостоятельная мини-инструкция, а не doorway**. Создать для неё файл `docs/seo/content-briefs.md` с полями: ID, интент, язык, согласованные ключевые варианты, целевой вопрос, проверенная функция, URL калькулятора, структура H1/H2, краткий пример, исключаемые утверждения, внутренние ссылки, источники, редакторская проверка.

### 13.1. Общий состав страницы

1. Один H1 отвечает пользовательскому вопросу; краткий ответ в первом экране (1–2 предложения).
2. Входные параметры: что посетитель должен знать/ввести (отличать подтверждённые данные от гипотез).
3. Короткое объяснение **что реально рассчитает Nomad360** с привязкой к V1, услуге или V2. Термины соответствуют действующему UI, а не общему учебнику MBA.
4. Практический пример: **условные данные обозначены как условные**, без обещания результата; вычисления и обозначения сверены с фактической моделью и локализованным интерфейсом.
5. Одна основная CTA-ссылка «Открыть расчёт», тематически понятная; по необходимости одна контекстная ссылка на соседнюю тему.
6. Ясная граница: результаты зависят от введённых данных, рыночный спрос не проверяется автоматически.
7. В конце — указание на бесплатность, приватность расчётов, отсутствие обязательной регистрации только там, где это соответствует реально используемому сценарию; **не дублировать большой лицензионный футер**.

Никаких искусственных требований «не менее 1000 слов»; текст должен полностью решать вопрос пользователя. Избегать кластера из 12 одинаковых страниц, подставляющих только «товар/услуга».

### 13.2. По темам

**A — business idea / бизнес-идея.** Вопрос: «При каких затратах, цене и количестве продаж моя идея способна приносить деньги?» Раскрыть исходные предположения, точку входа в товар/услугу, разницу между финансовым расчётом и рыночной проверкой спроса. Не обещать, что калькулятор выбирает лучшие ниши.

**B — pricing / цена.** Вопрос: «Как определить цену с учётом закупок, материалов, маркетинговых расходов и маржи?» Различать себестоимость, цену для покупателя, налоги и расходы бизнеса. Пример должен соответствовать признакам выбранной ветки V1.

**C — cash flow / денежный поток.** Вопрос: «Когда поступят деньги и хватит ли остатка на оплату обязательств?» Различать прибыль и денежный остаток; показать где выбирается горизонт, свои средства/кредит, какие данные пользователь задаёт сам; объяснить, что прогноз не равен подтверждённым будущим продажам. Для «нескольких товаров» показать отдельный переход к V2, не выдавать её за V1.

**D — consultants / для консультантов.** Вопрос: «Каким бесплатным инструментом можно заинтересовать предпринимателей на сайте бухгалтера или бизнес-консультанта?» Указать конкретные задачи аудитории (цена, расходы, денежный поток), бесплатный HTML как он есть, действующую кнопку скачивания и возможность собственной версии через существующий интерфейс **без разработки новой версии в этой задаче**. Не утверждать, что Nomad360 получает лиды клиента, гарантирует рост посещаемости или выполняет маркетинг вместо консультанта.

**Общие запреты:** скрытые лид-формы, автоматически собранные e-mail, вымышленные «отзывы клиентов», фиктивные результаты проверки бизнеса, необоснованные фразы «лучший/№1», копирование чужих статей и keyword stuffing.

## 14. Строгая спецификация метаданных, индексации и языков

### 14.1. Системная матрица метаданных

Для каждого `indexable` URL создать декларативную запись в общем SEO-манифесте данных (например, JSON/JS без финансовых функций):

- `id`, `locale`, `path`, `canonicalUrl`, `title`, `description`, `h1`;
- `hreflangGroup` / эквивалентные URL только опубликованных переводов;
- `robotsDirective` = индексировать по умолчанию, специальный `noindex` только при явно обоснованной служебной странице;
- `og:title`, `og:description`, `og:url`, `og:locale`, `og:image` — только реальные изображения;
- `primaryCtaHref`, `secondaryLinks` и `contentRevisionDate` (не выдумывать дату фактического обновления);
- `isPublished`: sitemap и hreflang автоматически исключают неопубликованные страницы.

При генерации исключить дубли `title` и `meta description` и отсутствие language-specific контента. Правильный пользовательский H1 на канонической странице приложения — утверждённый задачей 6; не производить автоподмену в JS только ради поисковых слов.

### 14.2. Пример проверки canonical/hreflang

Для `/shelter-partner-directory/en/` проверяемое ожидаемое содержимое `head`:

~~~html
<link rel="canonical" href="https://kazartsevev.github.io/shelter-partner-directory/en/">
<link rel="alternate" hreflang="en" href="https://kazartsevev.github.io/shelter-partner-directory/en/">
<link rel="alternate" hreflang="ru" href="https://kazartsevev.github.io/shelter-partner-directory/ru/">
<link rel="alternate" hreflang="kk" href="https://kazartsevev.github.io/shelter-partner-directory/kk/">
~~~

**Этот пример допустим только после появления всех трёх HTTP 200 страниц.** Если пока опубликован только EN — не добавлять ссылки hreflang на будущие RU/KK. На RU и KK тот же полный набор после публикации всех трёх, но свой `canonical`. Локализованные версии не канонизировать на EN только потому, что EN приоритетен. Не объявлять `x-default` произвольным синонимом EN; только при обоснованной нейтральной входной странице.

Для тематической статьи hreflang связывает **тот же интент** на разных языках, например `en/pricing/` ↔ `ru/pricing/` ↔ `kk/pricing/`. Не связывать `en/cash-flow/` с `ru/business-idea/` только из-за отсутствия перевода.

### 14.3. Судьба существующего Marketing_calc.HTML

Этот URL остаётся работающим полноценным приложением. Окончательно выбрать **одну из двух SEO-стратегий после сравнения контента**:
- отдельный application URL с **self-canonical**, потому что интерфейс и функциональность существенно отличаются от тематических страниц; RU0 отвечает более обзорному интенту;
- если RU0 на деле является почти точным текстовым дублем приложения, **не выпускать её в таком виде**: переработать в реальную тематическую страницу либо консолидировать URL по утверждённой карте, не ломая приложение.

Нельзя одновременно «склеить» все языковые страницы с `Marketing_calc.HTML` через canonical, указать взаимные hreflang и ожидать независимой индексации. `noindex` для приложения запрещён без отдельного письменного объяснения последствий и согласования владельца.

### 14.4. URL-параметры и дубли

- Демо-ссылки `?demo=shopper`, `?finance=cash`, `?finance=credit`, `?lang=...` не создавать как самостоятельные индексируемые страницы в sitemap.
- Составить матрицу canonical для тестовых и языковых параметров приложения. Не удалять параметр `demo` до инициализации тестового сценария. Если параметры не меняют самостоятельный поисковый контент, указывать основной URL приложения как canonical.
- Не создавать `/en/index.html` и `/en/` как разные «основные» URL с двумя несовместимыми canonical. Проверить, как реально отвечает GitHub Pages.
- Ошибочные пути должны возвращать реальный 404, не HTML «всё хорошо» со статусом 200. Кастомный `404.html` допустим, только если он не меняет поведение всего чужого проекта.

## 15. Sitemap, robots, служебные HTTP-ограничения: GitHub Pages project site

**Критическое правило:** `robots.txt` работает только по адресу **корня хоста** `https://kazartsevev.github.io/robots.txt`, а не `https://kazartsevev.github.io/shelter-partner-directory/robots.txt`. Поэтому создание `robots.txt` внутри этого репозитория **само по себе не даёт роботам правил для проекта**. Не считать такую операцию выполненной настройкой robots.

**Текущий контракт:**
- Проверить доступность `https://kazartsevev.github.io/robots.txt` и какие правила там действуют. Не изменять этот ресурс без отдельного решения владельца, так как затрагивает другие его сайты на hostname.
- Если hostname не запрещает обход проекта, для индексации достаточно реальных HTTP 200 страниц, обычных ссылок, отсутствия noindex и корректных метаданных; **наличие собственного robots.txt не является обязательным**.
- Сгенерировать `https://kazartsevev.github.io/shelter-partner-directory/sitemap.xml` с абсолютными canonical URL и фактической датой `lastmod` **только если она достоверно доступна из истории изменения содержимого**. Выдуманные ежедневные даты или одинаковый always-now запрещены.
- Не добавлять туда `index.html` (SHELTER), JS, CSS, README, query-параметры, 404, неиндексируемые технические страницы и неопубликованные языковые варианты.
- Сайтмап под project path можно отправить в Google Search Console вручную по полному URL при наличии подтверждённого доступа к ресурсу соответствующего URL-префикса. Ссылка Sitemap в host-root robots возможна **только если владелец контролирует этот файл и отдельно разрешил изменение**; без неё sitemap всё равно можно обнаружить через Search Console и внутренние ссылки.
- Проверить Content-Type, 200, XML parser и отсутствие ошибок namespace при использовании `xhtml:link` альтернатив.
- Если robots host-root запрещает данный project path, это блокер для индексации: отразить и запросить отдельное решение владельца; не обходить его с помощью скрытых зеркал.

**GitHub Pages:** проверить источник публикации (branch/folder vs GitHub Actions) **по настройкам/доказательствам**, не предполагать автоматически root/main. Проверить, что добавленные SEO-файлы действительно попадают в Pages artifact. Публикация всех файлов в Git не равна публикации на сайте.

## 17. Производительность, доступность и техническое качество

SEO-входы — **лёгкие статические страницы**, не должны загружать весь финансовый JS до действия пользователя. Основное приложение остаётся отдельным. Проверить исходный объём HTML/CSS/JS, сетевые запросы, шрифты и CLS. Не переписывать тяжёлое приложение ради баллов Lighthouse в рамках SEO-07.

**Целевые ориентиры Google Core Web Vitals** (в полевых данных, если они доступны): LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1 на 75-м процентиле; для новых страниц до появления полевых данных приёмка основана на воспроизводимом лабораторном аудите и отсутствии регрессий. Балл Lighthouse **не объявлять гарантией поискового ранжирования**.

Мобильные проверки 320/390/768/1280 px: таблицы не выходят за экран, фокус видим, ссылки и кнопки доступны с клавиатуры, без перекрытия CTA, заголовки и подписи корректного размера. Контент всегда доступен без consent-wall/логина. Если используются картинки — осмысленный alt и реальные оптимизированные файлы; если визуал не нужен — не добавлять декоративный сток ради «SEO».

Отдельная проверка privacy: **не встраивать счётчики, рекламные пиксели или внешние аналитические SDK**. Запросы браузера к уже используемым third-party ресурсам анализируются, но не маскируются как отсутствие внешних запросов. Финансовые значения не включать в URL, метаданные, страницу Search Console или sitemap.

## 18. Автоматизация контроля и точные тестовые сценарии Codex

Выполнить в существующем CI или отдельном тестовом шаге **без вмешательства в финансовые формулы**:

|---|---|---|
| SEO-01 | Статически запросить `en/`, `ru/`, `kk/` | Каждая HTTP 200, свой `lang`, свой title/description, ненулевой индексируемый H1 + релевантный текст без JS |

| SEO-04 | hreflang | Reciprocity: каждая группа страниц содержит эквиваленты и self; все href по HTTPS и HTTP 200 |
| SEO-05 | source vs DOM | После JS нет второго H1, смены смысла заголовка или кликабельных «пустышек» |
| SEO-06 | sitemap | Valid XML, все loc существуют, отвечают 200, self-canonical, без чужого проекта и query-параметров |
| SEO-07 | robots | Проверен **host-root robots**, нет блокировки проекта; файл в подкаталоге не засчитывается |
| SEO-08 | internal links | Все обязательные ссылки ведут к существующим целям, не к корню hostname и не к 404 |
| SEO-09 | language handoff | Из EN/RU/KK входа открывается именно выбранный язык реального калькулятора; ручная смена языка работает |
| SEO-10 | URL params | `demo=shopper`, `finance=cash`/`credit` работают вместе с `lang` и без него |
| SEO-11 | data continuity | Черновик не теряется при языке/ссылке/обновлении; не меняется денежная модель |
| SEO-12 | functional e2e | V1 товар, V1 услуга, V2 портфель, валюты, кредит/свои деньги, налоги, сохранение |
| SEO-13 | outputs | PDF/Excel доступны после валидного расчёта, Embed HTML скачивается со штатным сообщением/повторной ссылкой |
| SEO-14 | PR #141 | Счётчик 14-дневных уникальных посетителей GitHub продолжает отображаться без смены определения |
| SEO-15 | UX | Мобильные экраны, клавиатура, фокус, язык, CTA, контент без JS |
| SEO-16 | regression | `index.html` чужого проекта и `Marketing_calc.HTML` в старых адресах функционально неизменны |
| SEO-17 | GitHub Pages live | Повторить запросы после реальной публикации, не ограничиваться локальным server/fixture |
| SEO-18 | Search Console | Если есть доступ — URL inspection, индексация, выбранный canonical, sitemap; без доступа — чеклист вместо выдуманного статуса |

**Автоматизированный тест hreflang:** построить граф групп URL; у каждого набора проверить обратные ссылки, язык `en/ru/kk` и HTTP 200, отсутствие ссылок на неопубликованное. Тест sitemap проверяет идентичность canonical; тест метаданных — что DOM не переписывает основную семантику в другом языке.

**Приёмка производительности:** измерить LCP/INP/CLS где возможно и размер страницы; выявленные проблемы оформить как separate issues, если их исправление требует переделки приложения; не скрывать проблемы и не раздувать scope SEO-07.

## 19. Search Console, метрики и экспериментальный цикл без новых трекеров

### 19.1. Подключение для текущего GitHub Pages

Предпочесть URL-prefix property `https://kazartsevev.github.io/shelter-partner-directory/`, если Google разрешает и доступно подтверждение владения. Проверить существующие полномочия/верификацию; не выдавать «подключено» без факта. Для проверки через HTML-файл использовать **точно выданное сервисом имя и содержание файла**, положить его в публикуемый каталог проекта, проверить HTTP 200 и пройти верификацию. Не придумывать проверочный токен и не затрагивать корневой SHELTER-дизайн. Если метод для выбранного property не срабатывает, записать блокер и альтернативы через интерфейс Google; не изменять DNS github.io.

Отправить полный URL `https://kazartsevev.github.io/shelter-partner-directory/sitemap.xml`, подтвердить фактический статус обработки. Для каждой языковой входной страницы в URL Inspection: видит ли Google страницу, доступен ли контент, какая canonical выбрана, какие проблемы обнаружены. Наличие в sitemap **не гарантирует включения в индекс**.

### 19.2. Разделение метрик

| Источник | Что измеряется | Что НЕ измеряется |
|---|---|---|
| Search Console | Показы, клики, CTR, позиции, страницы, поисковые фразы и страны **в Google Search** | Все посещения сайта, скачивания и заявки |
| GitHub Insights / Traffic | Уникальные посетители **репозитория GitHub за 14 дней** | Пользователи калькулятора, просмотры GitHub Pages, лиды |
| Отчёт SERP/Wordstat/Planner (с датой) | Наблюдаемый спрос/объём по запросу и региону в конкретном инструменте | Реальные переходы на Nomad360 |
| Выполнение E2E | Работоспособность сценариев | Реальное коммерческое продвижение |

Отдельно отмечать branded/non-branded запросы, EN/RU/KK и entrepreneur/consultant интенты. Период 28 дней для удобства сравнения Search Console — только **пример периода отчёта**, а не предписанный обязательный KPI. При отсутствии достаточных данных честно писать «данных пока нет». Нельзя заявлять «спрос на калькулятор доказан» только из количества посетителей GitHub.

### 19.3. Правила оценки

- Факт индексации и реальный query coverage — измеряемые признаки попадания в поиск.
- Интерес конечного пользователя: появление показов/кликов по P0 financial-intent кластерам.
- Интерес консультантов: показы/клики на страницу `for-consultants` по релевантным B2B-фразам. Это **интерес**, не купленный/заказанный кастомный продукт и не «лиды».
- Рекомендации по содержимому формировать только после анализа реальных запросов и соответствующей выдачи. Никакого обязательного рекламного бюджета, e-mail-рассылок и коммерческих SLA.
- Следующие контентные страницы делать только по подтверждённому неудовлетворённому интенту; избегать производства SEO-страниц по расписанию ради количества.

## 20. Поставка Codex, границы PR и остановки

**Формат работ:** сначала отчёт об аудите URL, затем семантика и архитектура, затем EN, RU и KK. Не начинать следующую фазу до приёмки необходимых решений предыдущей; **всё в одном Draft PR задачи №7 либо в последовательных согласованных PR внутри задачи 7**, не менять main напрямую.

**Перечень файлов/артефактов, который должен появиться в PR:**
1. `docs/seo/serp-research.md` — запросы/дата/рынок/результат/источник/принятие или отклонение.
2. `docs/seo/url-map.md` — все старые/новые URL, canonical, status, связь эквивалентов.
3. `docs/seo/content-briefs.md` — состав каждой опубликованной страницы, её интент и проверки копирайтинга.
4. `docs/seo/verification-report.md` — матрица SEO-01–SEO-18 с фактическими результатами, скриншотами source/rendered, ошибки и открытые ограничения.
5. Опубликованные статические страницы EN/RU/KK и выбранные тематические страницы + минимальные шаблоны/ресурсы для их генерации.
6. Sitemap, технические тесты метаданных/внутренних ссылок/hreflang, минимальный контракт явного языка при переходе к калькулятору.
7. Список неизменённых защищённых файлов/функций и CI/E2E. Доказательство того, что `Marketing_calc.HTML` остаётся одним приложением.
8. Если что-то невозможно без изменения root-host ресурса GitHub, отдельное описание ограничений **без самовольного изменения root-host**.

**Не менять:** денежную математику, разметку маркетингового согласованного оффера, остальные продукты репозитория, код платежей, donation-виджет, юридическую атрибуцию, пользовательские данные, демонстрации, подсчёт посетителей GitHub. Вся правка SEO-кода направлена на discoverability, а не пересборку калькулятора.

**Остановка при неоднозначности:** если один и тот же выбранный URL предполагает замену SHELTER, если нужен домен или root robots, если новая страница не имеет честного функционального ответа, если инструмент аналитики потребует отправки расчётных данных третьим лицам — **не делать самовольной замены или сбора данных**; зафиксировать блокер в Draft PR с минимальными техническими вариантами.

**Критерий завершения именно ЗАДАЧИ №7:** подтверждённые EN/RU/KK indexable входы на GitHub Pages, рабочая архитектура ссылок к одному калькулятору, полные технические проверки и отчёт, отсутствие регрессий, подтверждённый безопасный scope относительно SHELTER; **индексация и позиции в Google не гарантируются и не являются поводом имитировать результат**. Выделенное отдельным этапом продвижение ссылками/рекламой и покупка домена не входят в PR.
