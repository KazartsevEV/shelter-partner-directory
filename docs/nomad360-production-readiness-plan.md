## Приоритетное уточнение владельца: ноль новых обязательных расходов · 26.10

**Эта редакция имеет приоритет над прежним требованием отдельного host/Redis.**
VPS, managed Redis, покупка домена и постоянно выделенный сервер не являются
обязательным baseline. Любой платный ресурс, billing enablement, перерасход,
подписка или продление — только после отдельного согласования владельца.
Free trial с последующей оплатой не считается нулевым бюджетом.

переработаны в Draft #504; **#504 не сливать в текущем цикле без новой приёмки**.
Прежний GREEN/локальные тесты #503 проверяют старую связанную Node-композицию,
а не новую zero-cost архитектуру. Автоматический merge/включение #503 приостановлены
на период архитектурной доработки; новые расходы не разрешены.

Статические расчёты/экспорты не требуют backend. Доверенный intake/ownership,
секреты и durable claims нужны, но не обязательно на новой машине. Первая
проверка — существующие ресурсы; Apps Script/function adapters только варианты,
не молчаливое переключение согласованного Node.js + Google. Windows runner может
собирать пакеты, но текущие POSIX guarded operator/state/leases на нём не работают
без адаптации. Google projection в Sheets не заменяет текущий полный state.

## Текущий независимый срез R4: перенос черновиков

[Локальная страница переноса](reviews/draft-transfer-r4/REVIEW.md) готовится отдельно
от финансовых форм: файл → проверка → preview → явное разрешение замены после
резервной копии. Сохранённые значения и версии не пересчитываются. Публикация на

Наличие этого кода не закрывает staging/TLS, действующие OAuth/WIF bindings, R1/P3,
проверки SEC-01 и реальную выдачу. Секреты и хостинг в этой задаче не создаются.

### R3 — приватная разработка и воспроизводимый выпуск

Целевой исходный репозиторий — существующий приватный `lazysellerV2`.
Выделить Nomad360 в собственный каталог и path-scoped CI, не затрагивая
Lazyseller/Infourok/Product Factory. Не переносить секреты, персональные заявки,
почтовые коды или рабочий state через Git. В заданиях приватной сборки — только
непрозрачный ID и допустимая конфигурация; контакты не передаются через Git.
Google хранит анкету/переписку, а закрытый host временно хранит зашифрованный
intake и минимальный контакт/состояние доставки; это надо явно раскрыть в
будущей политике и удалить по согласованному сроку во всех копиях.

Собирать отдельный публичный каталог сайта по проверяемому allowlist и манифесту
ресурсов. В него не входят `.git`, `.github`, `scripts`, `tests`, `docs/reviews`,
node_modules, оператор выдачи, настройки OAuth, state, заявки и ZIP партнёров.
Клиентские движки, необходимые UI, входят: скрытие репозитория не делает
JavaScript браузера секретным. Проверять полноту реальных динамических ресурсов,
автономный HTML и соответствие SHA, а не просто копировать расширения файлов.

Текущий `.github/workflows/static.yml` публикует `path: '.'`;
`.github/workflows/deploy-static.yml` — отдельный старый publisher с `index.html`.
Ни один не переносится как есть. Новая выдача в production имеет один явный
pipeline и каталог артефакта. Не менять публикацию чужого SHELTER `index.html`.

Приёмка: clean checkout → фиксированные зависимости → CI/сборка → проверенный
site artifact, release manifest, SHA и откат. В публичном артефакте нет запрещённых
файлов/секретов. Ручное скачивание текущего сайта продолжает работать до R6.

**WL-CICD-01, R3:** индивидуальные tenant profile/brand theme overlays, version manifest и path-scoped release workflow для разрешённого White Label клиента; тесты сохранности стилей и числовой совместимости обязательны. Не менять core под брендированием.

### R4 — существующая инфраструктура, бюджет и размещение

**Цель: ноль новых обязательных расходов.** До выбора VPS/нового домена составить
inventory: существующие площадки/hostname/DNS, ОС и доступность runner/машин,
Google accounts/grants/quotas/storage, GitHub billing/storage и свободная мощность.
Не читать/публиковать значения секретов. Наличие аккаунта/runner не равно праву
размещать production или достаточной квоте. Учитывать конкуренцию с Lazyseller.

Сравнить варианты: существующий разрешённый static hosting + пакетный Node worker;
имеющийся постоянно работающий узел; Google Apps Script intake/ledger + Node job;
согласованный ручной пилот; подходящий free-tier другой платформы после проверки
условий/лимитов. Новый аккаунт/провайдер не выбирается молча. При нехватке квоты
не включать платный перерасход автоматически.

Собственный новый домен не является воротами: использовать имеющийся допустимый
HTTPS origin/base path. Проверить условия GitHub Pages для commercial/SaaS —
не обещать безусловную пригодность существующей площадки. Не отключать текущий
сайт и не переносить его до согласованной альтернативы. Protected preview может
использовать существующий путь, не обязательно новый staging hostname.

На выбранном существующем адресе проверить URL/assets/Help/SEO/canonical/hreflang/
sitemap, RU/EN/KK, 320/360/390/430/768/desktop, local draft export/import и rollback.
Если remote endpoint недоступен — локальную проверку записать отдельно от
незакрытого HTTPS gate. Не обещать 301/308 с github.io без контроля сервера.
Ни state, ни финансовые drafts не отправляются через публичный Git.

Приёмка: подтверждённый ресурсный/стоимостной inventory, доступный без новой
обязательной платы вариант, его ограничения и неактивный fallback согласованы.
Если функция требует платной мощности — сравнение альтернатив и точная стоимость
сначала владельцу; без разрешения — не покупать/не подписываться.

**WL-CICD-01:** сначала synthetic/существующая клиентская инфраструктура. Реальные
права, два staging update и rollback проверяются на фактически доступном клиенте;
новый оплачиваемый клиентский host не создаётся ради прохождения теста.

### R5 — раздельные adapters на имеющихся ресурсах

Предпочтение Node.js + Google сохраняется, но постоянный платный сервер не
следует из него. **#503 как есть требует POSIX listeners/state и Unix Redis**;
этот вариант не объявляется совместимым с Apps Script/Windows/ephemeral function.
Ветка и старые тесты сохраняются как подготовленный вариант, не deployment mandate.

Порядок:

1. Проверить существующий совместимый узел без новых затрат. Если его нет —
   проектировать trusted intake/подтверждение отдельно от тяжёлой сборки.
2. Выбрать durable ledger/quota adapter и единый протокол claims для всех writer.
   Google Sheets/LockService — кандидат с ограничениями, не автоматическая
   атомарность для независимых Node API writers. In-memory замена Redis запрещена.
3. Node/Chromium/AES ZIP строится на доступном private runner/машине по запросу
   или расписанию. Существующий Windows runner требует cloud/Windows-compatible
   state/secrets/locking adapter; он не проходит POSIX production gate неизменённым.
4. Проверить Apps Script как intake/coordinator только при выборе этой альтернативы:
   quotas/6-minute execution, sender identity, endpoint access/abuse, redirects/CORS,
   UI transport и доверенный handoff. Это новый адаптер, а не готовый #503 backend.
5. Existing Formspree сохраняется до принятого переключения. Его обычный browser
   receipt не является аутентифицированным worker job; screenshot не отправляется
   в нынешний text-only канал. Не пересылать контакты в CI dispatch: только opaque ID.
6. Подключать существующие Google credentials штатным способом; service account
   не заменяет личный Gmail. Проверить реальные grants/quota/ACL и доставку.
   Новая подписка/Cloud project/billing не создаются без согласования.
7. Скриншоты и erasure — отдельные задачи/очереди: ограничения 5MiB/12MP,
   raster sanitisation/одно письмо, unknown outcome и все backup copies сохраняются.
   Если выбранный вариант не покрывает функцию, она остаётся выключенной.

Приёмка выбранного адаптера: durable idempotency/ownership/quota/security,
реальная заявка/реестр/письмо/ZIP/свой-чужой пароль/URL/retention/restart,
negative/replay/429/timeout и RU/EN/KK. Старые synthetic tests не заменяют эти
проверки. Допустимое ожидание и доступность worker указываются честно; ручной
режим и сокращение автоматизации требуют отдельной приёмки, не меняются незаметно.

Если лимит достигнут — backpressure/очередь/уведомление/согласованный ручной путь,
а не новая плата. Для действительно необходимого отдельного узла представить
техническое обоснование/замеры, альтернативы и их ограничения до выбора тарифа.

### R6 — включение только принятого варианта без новых обязательных расходов

Включать только выбранную и реально проверенную схему после R4/R5 и отдельной
приёмки. Новые домен/VPS/Redis/ежемесячная плата не являются условиями по умолчанию.
Любое новое платное обязательство требует отдельного решения до регистрации/
заказа/billing enablement; GREEN не является таким разрешением.

CTA/Help/licence/privacy/processors и обещания скорости/доступности отражают
фактическую архитектуру. Если принимается batch/manual pilot, описать именно его;
не обещать мгновенную автоматическую выдачу. До этого сохранить действующий
рабочий интерфейс/скачивание/условия, не включать фиктивную отправку.

Ранее выданные разрешения/копии не отзываются. Партнёрский профиль публикуется
только с отдельным согласием/проверкой. Код/private source остаётся в lazysellerV2,
public web-root — только проверенный artifact; не делать весь SHELTER repo приватным
и не выключать весь Pages. Сохранить старые ссылки, drafts, rollback и физическую
mobile-проверку. Переезд с нынешнего адреса необязателен, если он допустим для
согласованного сценария. После включения контролировать фактические квоты/расходы.

## SEC-01 — обязательный периметр доступности и anti-abuse (подготовка)

Подготовка SEC-01 **уже слита**: приватный [lazysellerV2 #492](https://github.com/KazartsevEV/lazysellerV2/pull/492) и документационный [#273](https://github.com/KazartsevEV/shelter-partner-directory/pull/273). Свойства SEC-01 сохраняются при выборе адаптера: доверенный intake, durable atomic limits и секреты вне клиента. Redis и конкретный CDN не становятся обязательной покупкой. Полная историческая спецификация в [SEC-01](security/SEC-01.md): Turnstile,
доверенный edge, серверные атомарные лимиты/квоты и CI. **Это подготовленный код, а
не действующая защита GitHub Pages**: CDN/WAF, домен, Google worker, Redis,
Turnstile-ключи и реальная почта не включены этим шагом.

- **R4 обязательный DoD:** настроенный проксируемый HTTPS-домен, WAF/DDoS,
  проверенный запрет прямого обхода edge на origin, различение статики/API,
  мониторинг и сценарий отката. Проверить тарифные ограничения провайдера.
- **R5 обязательный DoD:** публичная форма идёт через доверенный intake с
  серверным Turnstile Siteverify, отказ при ошибках, проверенная клиентская
  идентичность, общие атомарные лимиты, устойчивые к перезапуску квоты и
  idempotency для ZIP/Gmail/Google. Ограничить параллельные сборки,
  очередь, память, время, суммарные расходы. Не использовать in-memory-only
  throttle в multi-instance production.
- **R6 блокируется**, пока нет доказательств на собственном staging:
  запрещён прямой доступ к backend, проходят spoof/replay/quota/fail-closed
  проверки и контролируемые нагрузочные сценарии, доступен план реагирования.
  Не проводить DDoS-тестирование против GitHub Pages/третьих лиц.

Статус SEC-01 не заменяет работу R1/R2 и не разрешает меняющую DNS или
публичное скачивание публикацию.

**WL-CICD-01, R6:** коммерческий договор определяет срок и стоимость сопровождения, объём поддерживаемых обновлений, условия доступа к CI/CD и отдельной разработки новых функций. Публикация обещания и активация только после реальных e2e-проверок. Скриншотную форму публиковать только одновременно с работающей защищённой отправкой.

## 3. Что нельзя объявлять закрытым заранее

- Production-доставка и постоянный intake до R5.
- Миграция, домен, DNS, реальные HTTP-редиректы и эксплуатационный откат до R4/R6.
- Техническая защита от копирования браузерного JS: её не обеспечивает ни
  приватный Git, ни пароль ZIP. Серверный расчёт — отдельное изменение архитектуры,
  которое этот план не предусматривает.
- Автоматическая выдача без сайта до устранения описанного в R1 расхождения.
- Хранение данных «на GitHub», если фактически там только код/непрозрачные ID:
  публичная политика должна описывать реализацию, а не желаемое название сервиса.
